# 暗棋局域网对战

基于 Python、Flask、Flask-SocketIO、Eventlet 和 SQLite 的双人网页暗棋。前端使用原生 HTML、CSS 和 JavaScript，不需要 Node.js 或前端构建步骤。

> **阅读顺序：** 本文先介绍部署方法，再详细说明本项目实际实现的规则，最后提供代码结构与维护说明，便于后续开发者或 Agent 接手。

## 一、详细部署教程

### 1.1 环境要求

- Python **3.10 或更新版本**，以及 `pip`。
- 一台能被双方通过局域网访问的 Windows、Linux 或 macOS 电脑。
- 每位玩家各自使用现代浏览器。
- 当前页面会从 `cdn.socket.io` 加载 Socket.IO 浏览器客户端。Python 服务可以仅在局域网内运行，但浏览器仍需要访问该 CDN。若局域网完全离线，请参考[离线浏览器资源](#17-离线浏览器资源)。

不需要 Node.js、npm、前端打包工具或独立数据库服务。

### 1.2 解压并进入项目目录

解压项目压缩包，进入包含 `app.py`、`requirements.txt`、`templates/` 和 `static/` 的 `xiangqi-dark/` 目录：

```text
xiangqi-dark/
├── app.py
├── requirements.txt
├── README.md
├── README.zh-CN.md
├── LICENSE
├── templates/
│   └── index.html
└── static/
    ├── app.js
    └── style.css
```

以下命令默认都在 `xiangqi-dark/` 目录内执行。

### 1.3 创建 Python 虚拟环境

**Windows PowerShell：**

```powershell
py -3 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
```

如果 PowerShell 阻止执行激活脚本，可以改用命令提示符：

```bat
py -3 -m venv .venv
.venv\Scripts\activate.bat
python -m pip install --upgrade pip
```

**Linux 或 macOS：**

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
```

虚拟环境用于隔离当前项目的依赖，避免影响其他 Python 项目。

### 1.4 安装依赖

```bash
python -m pip install -r requirements.txt
```

当前依赖包括：

- `Flask`：HTTP 路由和 HTML 模板渲染。
- `Flask-SocketIO`：实时双向通信与对局事件。
- `eventlet`：`app.py` 中指定使用的 Socket.IO 异步服务后端。

若安装失败，请先检查是否已激活虚拟环境，以及 Python 版本和本机平台是否被相应依赖支持。不要随意删除 `requirements.txt` 中的 Eventlet：应用明确配置了 `async_mode="eventlet"`。

### 1.5 启动服务

```bash
python app.py
```

默认监听地址为 **`0.0.0.0:5000`**，因此同一局域网内的其他设备可以连接。服务器本机浏览器访问：

```text
http://127.0.0.1:5000
```

游戏期间请保持终端运行。结束服务时，在该终端按 **Ctrl+C**。

如需更改端口：

**PowerShell：**

```powershell
$env:PORT = "8080"
python app.py
```

**Linux/macOS：**

```bash
PORT=8080 python app.py
```

`PORT` 在服务器启动时读取。双方必须使用相同的主机地址和端口。

### 1.6 让局域网中的另一台设备连接

1. 查询服务器电脑的**局域网/私有 IP 地址**。Windows 执行 `ipconfig`，查找当前使用的网络适配器 IPv4 地址；Linux 可执行 `ip addr`；macOS 可在“网络”设置或通过 `ifconfig` 查看。
2. 确认双方在允许局域网设备互访的网络中。访客 Wi-Fi 或开启了客户端隔离的无线网络可能会阻止设备互连。
3. 对方在浏览器打开 `http://服务器局域网IP:5000`，并根据实际端口修改地址。
4. 双方分别设置昵称。一方创建房间并将五位房间号发给另一方，另一方输入房间号加入。

**防火墙：** Windows 首次运行时，可允许对应 Python 程序或在可信的“专用网络”中放行 TCP 5000 端口。如使用其他端口，应放行相应端口。只对可信网络开放，不要为了排查问题而全局关闭防火墙。

### 1.7 离线浏览器资源

当前 `templates/index.html` 从 `https://cdn.socket.io/4.8.1/socket.io.min.js` 加载浏览器端 Socket.IO。服务器本身可以只在局域网中运行，但浏览器仍须能取得这段 JavaScript。如果局域网没有互联网连接：

1. 获取与当前 Flask-SocketIO 服务端兼容的 Socket.IO 4.x 浏览器客户端。
2. 将压缩后的客户端文件放到 `static/socket.io.min.js`。
3. 修改 `templates/index.html` 末尾的脚本引用，把 CDN URL 改为 `/static/socket.io.min.js`。
4. 在分发版本前，重新加载页面并测试两名玩家能否正常连接。

不要未经测试就使用来源不明或版本随意的客户端文件。

### 1.8 持久化数据与重启恢复

应用会在 `app.py` 所在目录中创建 SQLite 数据库和 Flask 会话密钥：

- **`players.sqlite3`**：`players` 表保存昵称和玩家当前对局标记；`games` 表保存未结束对局的序列化状态。
- **`.flask_secret_key`**：若未设置环境变量 `SECRET_KEY`，首次启动时会自动生成。它用于签名浏览器的 Flask 会话 Cookie，其中包含持久化玩家 ID。

升级或重启时请保留这两个文件。删除数据库会丢失已保存的玩家和对局状态；更换会话密钥会使既有签名 Cookie 失效，服务器可能无法再识别原玩家。如果玩家清除了浏览器 Cookie 或网站数据，服务器也无法把该浏览器和此前的玩家 ID 关联起来。

服务器启动时会从 SQLite 恢复未结束的棋局并保留双方座位。浏览器使用原会话 Cookie 重新连接后，Socket.IO 的 `connect` 处理器会将新的 socket ID 绑定到原座位并推送最新状态。`games.state_json` 会保存棋盘、回合、吃子列表、走棋记录、最近一步、悔棋历史、待处理申请和申请拒绝锁。

**安全升级步骤：**

1. 在终端按 Ctrl+C 停止服务。
2. 将 `players.sqlite3` 和 `.flask_secret_key` 备份到私密位置。
3. 更新源代码，但把以上两个数据文件保留在项目目录中。
4. 激活虚拟环境；如果依赖有变化，重新执行 `python -m pip install -r requirements.txt`。
5. 执行 `python app.py` 启动，并测试双人对局、刷新重连和服务器重启恢复。

不要把 `players.sqlite3`、`.flask_secret_key`、`.env` 或虚拟环境目录提交到版本控制中。

### 1.9 可选：设置稳定的会话密钥

可以不使用自动生成的密钥文件，而是通过环境变量 `SECRET_KEY` 配置一段足够长、随机且保密的值。它必须在服务器重启后保持不变；如果使用多个实例，每个实例必须配置相同的值。可通过以下命令生成：

```bash
python -c "import secrets; print(secrets.token_hex(32))"
```

将命令结果设置到启动环境中的 `SECRET_KEY`，不要把生产密钥直接写进源代码或公开仓库。若未设置环境变量，程序会自动使用 `.flask_secret_key`。

### 1.10 常见问题排查

| 现象 | 排查内容 |
|---|---|
| 找不到 `python` 命令 | 安装 Python 并重新打开终端；Windows 可尝试 `py -3`。 |
| 出现 `ModuleNotFoundError` | 激活 `.venv`，然后重新执行 `python -m pip install -r requirements.txt`。 |
| 服务器本机也打不开网页 | 检查启动终端的报错、端口配置，尝试 `http://127.0.0.1:5000`。 |
| 本机可用，另一台设备无法连接 | 检查服务器 LAN IP、网段、访客网络/客户端隔离、操作系统防火墙和端口。对方设备不能用 `127.0.0.1` 访问服务器。 |
| 页面能打开，但连接状态始终断开 | 检查浏览器开发者工具及 Socket.IO CDN 是否可访问；必要时按上文改为本地资源。 |
| 玩家无法回到原对局 | 保留浏览器 Cookie、`players.sqlite3` 和 `.flask_secret_key`；检查是否更换了访问主机名/会话，并查看服务器日志。 |
| 更新后对局消失 | 停止使用有问题的版本并恢复数据库备份。修改 `serialize_game()` / `deserialize_game()` 时必须兼容旧版保存数据。 |

### 1.11 部署与安全边界

本项目针对可信局域网娱乐和二次开发，**不是经过加固的公网服务**。它没有账号密码体系、TLS 终止、请求频率限制、滥用防护，也没有多工作进程共享的 Socket.IO 状态。不要直接将 5000 端口暴露到公网。若要公开部署，应先设置生产反向代理，并补充认证、TLS、请求防护、限流以及共享 Socket.IO 消息队列/会话方案。

项目使用进程内的 `rooms` 字典和 SQLite 持久化，按**单个应用进程**设计。SQLite 能让对局在进程重启后恢复，但不会自动让多个 worker 共享内存中的实时房间状态。

## 二、详细游戏规则

以下是本项目代码实际实现的规则，包含自定义暗棋机制；它并不完全等同于标准中国象棋。

### 2.1 棋盘、阵营和初始布局

- 棋盘为 **9 列 × 10 行**，棋子位于棋盘网格的交点。
- 双方分别为**红方**和**黑方**，红方先行。
- 每方共 16 枚棋子：帅/将 1 枚、仕/士 2 枚、相/象 2 枚、马 2 枚、车 2 枚、炮 2 枚、兵/卒 5 枚。
- 双方的帅/将固定在己方底线中央并保持明置；每方其余 15 枚棋子初始时朝下。
- 每方这 15 枚棋子的**真实棋种会在该方预设的 15 个初始格之间随机打乱**。朝下棋子的走法最初绑定其所在初始格对应的标准象棋棋种，而不是其隐藏的真实棋种。这是本项目的核心变体。

### 2.2 回合与翻开机制

1. 轮到自己时，只能移动己方棋子。
2. 服务端会校验所有走法。浏览器中点击棋子和目标格并不会让非法走法变为合法。
3. 朝下棋子按照其**初始格绑定的走法**移动。在棋盘上，它的真实棋种对双方都隐藏，包括对棋子拥有者本人。
4. 朝下棋子首次成功移动时（包括首次移动就吃子），该棋子翻开。此后的走法按它**实际显示出的棋种**计算。
5. 满足相应走法规则时，可以移动到对方棋子所在格并吃子。不能吃掉己方棋子。
6. 吃掉对方的帅/将即刻获胜。

帅/将初始时明置，其他棋子初始时均为暗棋。

### 2.3 棋子走法

下表描述**明棋**的走法；朝下棋子尚未移动时，也使用对应初始格所绑定的走法。

| 棋子 | 本项目中的走法 |
|---|---|
| **车** | 沿横向或纵向移动任意格数，起点与终点之间不能有其他棋子。 |
| **炮** | 沿横向或纵向移动。普通移动时起点与终点之间不能有棋子；吃子时必须且只能隔着一枚棋子（炮架）。 |
| **马** | 走日字，即一轴走两格、另一轴走一格；对应的蹩马腿位置必须为空。 |
| **相/象** | 沿对角线一次移动两个交点；中间的象眼必须为空。**与标准象棋不同，本项目允许象过河。** |
| **仕/士** | 沿对角线移动一格。**与标准象棋不同，本项目允许士离开九宫并过河。** |
| **帅/将** | 通常在己方九宫内沿横向或纵向移动一格。九宫为第 4–6 列；黑方第 1–3 行，红方第 8–10 行。此外，若对方将帅与己方将帅处于同一列且中间没有棋子，可以沿该列直接吃掉对方将帅。吃掉后立即结束对局。 |
| **兵/卒** | 在己方九宫外，每次向前走一格；过河后也可改为横向走一格。**自定义规则：明置的兵/卒若从己方九宫内部起步，可向上、下、左、右任意一个方向移动一格。**不能斜走。 |

**方向与过河判定：** 红方向棋盘上方前进，黑方向棋盘下方前进。红方当前行索引 `y <= 4` 时视为已过河；黑方当前行索引 `y >= 5` 时视为已过河。兵/卒是否处于己方九宫内，以**当前起点格**判断。

### 2.4 吃子时的信息显示

- 棋盘显示棋子的所属方，但暗棋棋种不显示。
- 被吃的明棋会显示其棋种。
- 如果被吃的是暗棋，**吃子方**可以在自己的被吃棋子列表中看到其真实棋种；被吃方看到的仍是未知的“暗子”记录，不会因对方吃子而得知其棋种。
- 服务端始终保留完整棋盘，但会向每名玩家发送经过过滤的状态快照。修改快照或吃子列表的过滤逻辑时需格外谨慎，避免把暗棋信息泄漏给浏览器。

### 2.5 悔棋申请（撤销两个半回合）

- 只有在**申请方自己的回合**、双方都已进入房间、至少完成两步有效行棋且没有其他待处理申请时，才能申请悔棋。
- 对方页面会显示应用内的 alert 风格弹窗，必须选择“同意”或“拒绝”。
- 对方同意后，撤销最近**两步行棋**，正常轮流行棋时即双方各撤销一步。棋盘、回合、吃子列表、行棋记录及最近一步标记均恢复到这两步之前。
- 对方拒绝后，申请方在当前回合内不能再次申请悔棋。回合序号推进后，该限制解除。
- 悔棋历史和待处理申请会保存到 SQLite，服务器重启后也不会自动丢失。

### 2.6 申请平局

- 申请方只能在自己的回合，且双方均在房间中、没有其他待处理申请时申请平局。
- 对方必须在应用内弹窗中明确同意。对方同意后，本局以平局结束；拒绝后继续游戏。
- 被拒绝后，申请方在当前回合内不能再次申请平局。平局与悔棋的拒绝限制分别记录。

### 2.7 投降与对局结束

- 双方都已加入后，任意一方都可以投降。投降立即结束对局，由对方获胜，不需要对方同意。
- 吃掉对方帅/将也会立即结束对局。
- 双方同意平局后以 `draw` 结果结束。
- 对局结束后，双方的进行中标记和已保存的未结束棋局记录都会清除；已结束的对局不会自动恢复。

### 2.8 最近一步、行棋记录与申请锁定

- 最近一步行棋的起点和终点会以绿色虚线圆框标出。
- 侧栏展示走棋记录及双方各自吃到的棋子。
- 悔棋或平局申请待处理期间，双方都不能走棋；只有收到申请的一方可以回复。过期或 ID 不匹配的请求会被服务端拒绝。
- 界面会在不满足条件时禁用按钮，但服务端仍会再次校验所有关键条件。

### 2.9 尚未实现的规则

这是一个自定义休闲游戏，不是完整的竞赛象棋引擎。当前没有：

- 将军、将死检测，也不强制玩家走棋时保护己方帅/将。
- 重复局面、步数或其他正式的象棋和棋裁定；和棋通过申请并经对方同意完成。
- 计时、AI 对手、观战或除房间号加入以外的自动匹配功能。

## 三、代码结构与接手须知

### 3.1 文件结构

- `app.py`：权威游戏服务端，包括 Flask 路由、Socket.IO 事件、棋盘初始化、走法校验、房间管理、申请流程和 SQLite 持久化。
- `templates/index.html`：页面结构、棋盘 SVG 线条、操作按钮、侧栏及申请弹窗。
- `static/app.js`：Socket.IO 客户端、前端临时状态、棋盘绘制、申请弹窗和用户交互。它不是走法合法性的权威来源。
- `static/style.css`：木色棋盘与棋子样式、响应式布局、状态标记、弹窗和提示框样式。
- `requirements.txt`：Python 依赖及版本范围。
- `README.md`：英文部署、规则和维护说明。
- `LICENSE`：MIT 许可证。
- `AGENTS.md`：供后续编码 Agent 遵循的项目约束和检查清单。

### 3.2 服务端数据模型

- `Piece(kind, side, face_up, move_kind)`：`kind` 是真实棋种；`move_kind` 是初始格绑定的走法；`face_up` 决定 `legal_move()` 当前使用哪一个。
- `GameRoom`：棋盘、玩家座位、回合、吃子列表、行棋日志、悔棋快照、最近一步、行棋/回合计数、待处理申请和拒绝锁。
- `rooms`：以房间号为键的进程内字典。SQLite 用于进程启动时恢复对局，但实时状态仍保存在内存中。
- `players` 表：保存稳定的浏览器/会话 `player_id`、昵称、`in_game`、`room_code`、`side`。**该表的列名叫 `sid`，但其中存的是持久化玩家 ID，而不是当前 Socket.IO SID。** 浏览器重连时，实时 socket ID 会被替换。
- `games` 表：每个未结束房间保存一份 `state_json` 序列化状态。

`db()` 负责创建表并迁移旧版本的玩家对局状态列。`serialize_game()` / `deserialize_game()` 定义对局存档格式。`load_persisted_rooms()` 在启动时恢复房间；`restore_player_room()` 在 Socket.IO 连接后重新绑定已保留的座位。

### 3.3 Socket.IO 事件接口

客户端发送给服务端：

| 事件 | 用途 |
|---|---|
| `set_nickname` | 设置/更新当前 Flask 会话的昵称。 |
| `create_room` | 创建房间并将创建者设为红方。 |
| `join_room` | 加入已有房间，第二名玩家执黑。 |
| `move` | 提交 `from` / `to` 棋盘坐标，由服务端校验。 |
| `request_undo` | 请求对方撤销最近两步行棋。 |
| `request_draw` | 请求对方同意和棋。 |
| `respond_request` | 使用申请 ID 回复同意或拒绝。 |
| `surrender` | 结束对局并判对方获胜。 |

服务端发给客户端：

| 事件 | 用途 |
|---|---|
| `nickname_ok` | 昵称已接受。 |
| `room_joined` | 分配或恢复房间号与阵营。 |
| `state` | 针对当前玩家过滤过的对局状态快照。 |
| `notice` | 操作结果或错误提示。 |
| `request_result` | 玩家所发申请的处理结果。 |
| `room_ended` | 通知对局结束并让页面返回大厅。 |

`state` 的内容与查看者有关，必须保留暗棋与吃子信息的隐私规则。若新增 `GameRoom` 持久化字段，需要同步修改序列化和反序列化、为旧存档提供安全默认值，并检查悔棋快照是否也需要恢复该字段。

### 3.4 建议的开发与测试流程

1. 在真实存档上运行测试前，备份 `players.sqlite3` 和 `.flask_secret_key`。
2. 走法规则应主要修改 `legal_move()` 或相应的服务端事件，不能只在 JavaScript 中限制。
3. 增加持久化状态时，检查 `GameRoom`、`serialize_game()`、`deserialize_game()`、适当的状态快照以及悔棋前后状态的保存/恢复逻辑。
4. 检查语法：`python -m py_compile app.py`；如果安装了 Node.js，再执行 `node --check static/app.js`。
5. 使用两台设备或两个浏览器测试建房/加入、合法与非法走棋、暗棋信息、吃子、申请同意/拒绝、撤销两步、页面刷新重连和服务器重启恢复。
6. 提交代码前确认没有包含 SQLite 数据库、会话密钥、浏览器状态转储或其他本地运行数据。

语法检查不能替代双人浏览器联机测试，尤其是 Socket.IO 事件顺序和重连流程。
